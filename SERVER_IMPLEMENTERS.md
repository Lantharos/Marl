# PIG Remote Server Implementer Guide

This document defines the current remote server contract for PIG.

The goal is straightforward: any server that implements this contract should be able to accept `pig login`, `pig remote add`, `pig sync`, and future sty.sh-hosted sync traffic without requiring CLI changes.

This is the v1 remote protocol. It is intentionally small, workspace-scoped, and built around content-addressed object transfer.

## Scope

This document covers:

- authentication requirements
- required HTTP endpoints
- request and response shapes
- object storage expectations
- workspace head semantics
- compare-and-set rules
- sync behavior expected by the current CLI

This document does not cover:

- project hosting UI
- issues, discussions, permissions beyond token validity
- CI hooks
- merge request workflows
- real-time collaboration

## Core model

The current remote model is:

- one project contains many workspaces
- each workspace is identified by its workspace name in v1
- each workspace has one remote head snapshot id
- objects are content-addressed and immutable
- the remote stores blobs, trees, and snapshots
- sync transfers missing objects, not file diffs

The CLI assumes the remote can answer:

- what is the current head of workspace `X`
- how does local head `Y` relate to remote head `Z`
- which object ids does the remote already have
- can the remote accept these missing objects
- can the remote update a workspace head only if it still points at the expected old head

## Authentication

The CLI currently uses bearer token auth.

Every authenticated request includes:

```http
Authorization: Bearer <token>
```

If the token is missing or invalid, the server should return:

- `401 Unauthorized` or
- `403 Forbidden`

The CLI treats either status as `auth_required`.

## Tenant and project identity

The client addresses remotes as `tenant/project`.

- `tenant` is a user or organization namespace
- `project` is the human-readable project name inside that tenant

The current CLI stores:

- auth system-wide during `pig login`
- auth can also be imported non-interactively through `pig auth import <remote-url> --token-stdin`
- repo-to-remote mapping during `pig remote add <tenant>/<project>`

The remote may internally map those names to internal ids, but the protocol boundary is name-based.

## OAuth handoff for sty and other CLIs

The intended integration path for a host CLI such as `sty` is:

1. `sty` completes the browser or device OAuth flow itself
2. `sty` obtains a bearer token that is valid for the PIG remote API
3. `sty` shells out to:

```text
pig auth import <remote-url> --token-stdin
```

4. `sty` writes the token to PIG over stdin
5. the user is now authenticated in PIG system-wide
6. repo setup still happens separately with:

```text
pig remote add <tenant>/<project>
```

This means users do not need to hunt for a dashboard token manually, and PIG does not need to own the OAuth browser flow itself.

From the server side, this does not require a special new endpoint. It only requires that the OAuth flow can mint or exchange into a bearer token accepted by the standard PIG API endpoints documented below.

## Workspace identity

Workspaces are addressed by workspace name in v1.

That means the server must treat this path segment as the workspace key:

```text
/v1/tenants/{tenant}/projects/{project}/workspaces/{workspace}/...
```

If you later add internal workspace ids, keep accepting workspace names at the protocol boundary unless the client contract is revised.

## Object model

The remote stores three object kinds:

- `blob`
- `tree`
- `snapshot`

Object ids are SHA-256 hex digests generated by the client.

Objects are immutable. If an object id already exists, storing the same bytes again must be a no-op.

### Blob object

Blobs are raw file bytes.

The server does not need to understand blob contents.

### Tree object

Tree objects are JSON with this shape:

```json
{
  "entries": [
    { "name": "src", "id": "<object-id>", "entry_type": "tree" },
    { "name": "main.rs", "id": "<object-id>", "entry_type": "blob" }
  ]
}
```

`entry_type` is currently:

- `blob`
- `tree`

### Snapshot object

Snapshot objects are JSON with this shape:

```json
{
  "id": "<snapshot-id>",
  "parents": ["<snapshot-id>", "<snapshot-id>"],
  "kind": "save",
  "author": "krist",
  "agent": null,
  "agent_model": null,
  "time": "2026-04-11T14:43:14.8564121Z",
  "message": "initial",
  "root_tree": "<tree-id>",
  "workspace_id": "main",
  "intents": [
    {
      "intent_type": "modified",
      "unit": "function",
      "name": "alpha",
      "file": "src/app.ts",
      "line_start": 1,
      "line_end": 4
    }
  ]
}
```

Notes:

- `id` may be blank in pre-hash payloads produced before the client rewrites the stored object, but objects uploaded during sync should already contain the final id
- `parents` may contain zero, one, or multiple snapshot ids
- `kind` is client-defined metadata such as `save`, `cram`, `merge`, `pre-merge`, or `sync-merge`
- `workspace_id` is client metadata and should be stored but does not drive remote routing
- `intents` are opaque to the server in v1

## Required endpoints

### 1. Auth check

```http
POST /v1/auth/check
```

Purpose:

- validate token
- validate remote availability

Request body:

- empty body is acceptable
- `{}` is acceptable

Success response:

```json
{ "ok": true }
```

Failure:

- `401` or `403` if auth is invalid

### 2. Workspace head

```http
GET /v1/tenants/{tenant}/projects/{project}/workspaces/{workspace}/head
```

Purpose:

- return the current remote head for that workspace

Success response:

```json
{ "head": "<snapshot-id-or-null>" }
```

The current CLI does not actively call this endpoint yet, but it is part of the documented protocol and worth implementing.

### 3. Compare local vs remote

```http
POST /v1/tenants/{tenant}/projects/{project}/workspaces/{workspace}/compare
```

Request body:

```json
{ "local_head": "<snapshot-id-or-null>" }
```

Success response:

```json
{
  "remote_head": "<snapshot-id-or-null>",
  "relation": "same | local_ahead | remote_ahead | diverged | remote_missing"
}
```

#### Relation semantics

`same`

- local head equals remote head

`local_ahead`

- remote head exists
- remote head is an ancestor of local head

`remote_ahead`

- local head exists or is null
- local head is an ancestor of remote head

`diverged`

- both sides have heads
- neither head is an ancestor of the other

`remote_missing`

- remote workspace has no head yet

#### Ancestry rules

The server must compute ancestry using snapshot parent links.

The client assumes:

- a snapshot can have multiple parents
- ancestry walk is over snapshot parents only
- trees and blobs do not participate in ancestry

### 4. Missing object negotiation

```http
POST /v1/tenants/{tenant}/projects/{project}/objects/missing
```

Request body:

```json
{
  "ids": ["<object-id>", "<object-id>"]
}
```

Success response:

```json
{
  "missing": ["<object-id>", "<object-id>"]
}
```

Rules:

- return only the subset the server does not already have
- preserve input order if convenient, though the client does not require it

### 5. Object upload

```http
POST /v1/tenants/{tenant}/projects/{project}/objects/upload
```

Request body:

```json
{
  "objects": [
    {
      "id": "<object-id>",
      "kind": "blob | tree | snapshot",
      "bytes_base64": "<base64-encoded-bytes>"
    }
  ]
}
```

Success response:

```json
{ "ok": true }
```

Rules:

- uploads are idempotent
- if an object already exists, accept it without error
- the server should store both the object kind and raw bytes
- the server does not need to trust the client blindly forever, but the current client assumes successful uploads are stored exactly as sent
- clients may split missing objects across multiple upload requests; servers should not require every object for a sync to arrive in one request

Recommended validation:

- verify `id` matches SHA-256 of decoded bytes
- reject malformed base64
- reject unknown `kind`
- enforce request-size limits per upload request instead of per sync operation

### 6. Chunked object upload

Large objects may be uploaded without JSON/base64 by sending raw byte chunks under the final content id.

```http
PUT /v1/tenants/{tenant}/projects/{project}/objects/{object-id}/chunks/{chunk-index}
```

Request headers:

- `Authorization: Bearer <token>`
- `x-pig-object-kind: blob | tree | snapshot`
- `x-pig-chunk-count: <number-of-chunks>`
- `x-pig-total-size: <raw-byte-size>`

Request body:

- raw bytes for this chunk

Then finalize:

```http
POST /v1/tenants/{tenant}/projects/{project}/objects/{object-id}/complete
```

Request body:

```json
{
  "kind": "blob | tree | snapshot",
  "total_size": 123,
  "chunk_count": 4
}
```

Rules:

- chunks are zero-indexed
- finalization must assemble chunks in index order
- finalization must verify the assembled raw bytes hash to `{object-id}`
- if the object already exists, chunk upload and finalization should be idempotent no-ops
- once finalization succeeds, the object must be visible to `objects/missing`, `objects/download`, and head updates just like JSON-uploaded objects

### 7. Object download

```http
POST /v1/tenants/{tenant}/projects/{project}/objects/download
```

Request body:

```json
{
  "ids": ["<object-id>", "<object-id>"]
}
```

Success response:

```json
{
  "objects": [
    {
      "id": "<object-id>",
      "kind": "blob | tree | snapshot",
      "bytes_base64": "<base64-encoded-bytes>"
    }
  ]
}
```

Rules:

- return the requested objects
- the current client may request one id at a time while traversing a missing closure
- returning fewer objects than requested is treated as an error if the requested object is absent from the response

### 8. Compare-and-set head update

```http
PUT /v1/tenants/{tenant}/projects/{project}/workspaces/{workspace}/head
```

Request body:

```json
{
  "expected_head": "<snapshot-id-or-null>",
  "new_head": "<snapshot-id>"
}
```

Success response:

```json
{ "ok": true }
```

Conflict response:

- return `409 Conflict` when the current remote head does not equal `expected_head`

Auth failure:

- return `401` or `403`

Rules:

- this is the only write that advances workspace state
- the server must not silently overwrite a workspace head when `expected_head` does not match

## Sync behavior expected by the client

### Push path

When compare returns `local_ahead` or `remote_missing`, the client will:

1. enumerate all objects reachable from the local head
2. call `objects/missing` in bounded id batches
3. upload only the missing object ids in bounded object batches, using chunked upload for large objects
4. call CAS head update with:
   - `expected_head = current remote head`
   - `new_head = local head`

If CAS fails once, the client re-runs compare and retries the sync flow once.

### Pull path

When compare returns `remote_ahead`, the client will:

1. traverse from the remote head snapshot id
2. download any missing snapshots, trees, and blobs
3. update the local workspace head
4. restore the local working tree

The server only needs to provide object bytes and the remote head. The working-tree restore is local-only.

### Diverged path

When compare returns `diverged`, the client will:

1. download the missing remote object closure
2. compute the common snapshot ancestor locally
3. run its local semantic merge engine
4. if the merge auto-resolves:
   - create a new local `sync-merge` snapshot
   - upload its reachable object closure
   - CAS-update the remote head to the merged snapshot
5. if the merge conflicts:
   - persist a local merge attempt artifact
   - resolve locally through CLI/TUI
   - on finalize, upload the merged result and CAS-update the remote head

This means the server does not perform conflict resolution in v1.

## Error handling expectations

The current CLI treats these cases specially:

- `401` or `403` from any authenticated endpoint: `auth_required`
- `409` from head update: CAS conflict, not a fatal protocol error

All other non-200 responses should include a response body if possible, because the client surfaces the raw body text in generic failures.

Recommended error shape:

```json
{
  "error": "human-readable message"
}
```

The client does not currently require a structured error schema beyond the status code.

## Server storage recommendations

Any storage model is fine if these invariants hold:

- objects are keyed by content id
- workspace heads are mutable refs
- compare can answer ancestry questions over snapshot parents
- uploads are idempotent
- CAS head update is atomic

One practical layout:

- `projects`
- `workspaces`
- `workspace_heads`
- `objects`
- `snapshot_edges`

Where:

- `objects` stores `id`, `kind`, and bytes
- `snapshot_edges` stores parent relationships extracted from snapshot bytes to support compare efficiently

You can also compute ancestry lazily from stored snapshot bytes, but indexing parents will make compare much cheaper.

## Validation recommendations

The current client does not require all of these checks, but a production server should strongly consider them:

- SHA-256 verification for uploaded object ids
- object kind validation
- snapshot JSON schema validation for `snapshot` objects
- tree JSON schema validation for `tree` objects
- max upload batch size
- max object byte size
- token-to-project authorization

## Concurrency rules

The key concurrency guarantee is the CAS workspace head update.

If two clients race:

- both may upload objects safely
- only one may successfully advance the workspace head for a given expected value
- the loser must receive `409 Conflict`

This is what keeps `pig sync` from silently overwriting remote progress.

## Compatibility notes

The current CLI already implements:

- `pig login`
- `pig remote add`
- `pig sync`
- object upload/download
- batched object upload
- chunked upload for large objects
- compare handling
- local auto-merge on divergence
- local conflict resolution for sync conflicts

That means any server implementing the contract above can be tested immediately with the current client.

## Minimal smoke test checklist

Before calling a server implementation complete, verify these flows:

1. auth check succeeds with a valid token
2. auth check fails with an invalid token
3. first sync to an empty remote returns `remote_missing` and accepts a push
4. a second repo can compare and pull `remote_ahead`
5. compare returns `local_ahead` when remote head is an ancestor of local head
6. compare returns `diverged` when two descendants share a common ancestor
7. head update returns `409` when `expected_head` is stale
8. object download returns valid bytes for snapshots, trees, and blobs

## Future-compatible extensions

If you want to extend the server without breaking the current client, these are safe:

- adding response fields the client ignores
- adding stricter validation on malformed uploads
- indexing intents for remote-side search
- storing workspace ids in addition to names
- adding project metadata and permissions

These would require a client contract change:

- changing endpoint paths
- renaming relation values
- replacing bearer auth without backward compatibility
- changing object serialization format
- requiring a separate fetch-only step instead of `sync`

## Summary

If your server:

- accepts the seven endpoints above
- stores immutable objects by content id
- tracks mutable workspace heads
- answers ancestry-based compare requests correctly
- performs atomic CAS head updates

then it is a valid PIG remote for the current CLI and a solid base for later sty.sh integration.
